## Conventions

- Base path: `/api/v1`
- JSON only. Field names are `snake_case`.
- IDs are UUIDs, generated by the client for creates so retries are idempotent.
- Money is an integer in minor units (sen; 1 MYR = 100 sen) with a `currency` field.
- `currency` is an ISO 4217 three-letter code and defaults to `MYR` when omitted. Only `MYR` is accepted for now; any other value returns `400 validation_error` (multi-currency is out of scope).
- Distances are integers in kilometres. This includes `odometer`.
- Timestamps are ISO 8601 UTC. Dates are `YYYY-MM-DD`.
- All endpoints except `/health` need `Authorization: Bearer <token>`.
- Every response under `/api` (including errors) carries `Cache-Control: no-store`.
- Request bodies larger than 64 KiB (65,536 bytes) are rejected with `400 validation_error` and a detail `{ "field": "body", "issue": "request body is too large" }`.
- Upper bounds (violations return `400 validation_error`): `odometer` <= 10,000,000 km; every `*_minor` money field (`cost_minor`, `purchase_price_minor`) <= 10^12 sen.

## Error shape

```json
{
  "error": {
    "code": "validation_error",
    "message": "Human-readable summary",
    "details": [{ "field": "cost_minor", "issue": "must be >= 0" }]
  }
}
```

| Status | Code | Meaning |
|---|---|---|
| 400 | `validation_error` | Body failed validation |
| 401 | `unauthenticated` | Missing or invalid token |
| 404 | `not_found` | Resource does not exist |
| 405 | `method_not_allowed` | HTTP method not supported on this path |
| 409 | `conflict` | Same ID with different content |
| 429 | `rate_limited` | Too many failed login attempts. Response has a `Retry-After` header in seconds. The login attempt is refused even if the password is correct (hard lockout, owner decision) |
| 500 | `internal_error` | Unexpected server error. Uses the same error shape; `details` is empty and no internal information is exposed |

## Endpoints

### Health

`GET /health` returns `200 {"status": "ok"}`. No authentication.

### Authentication

`POST /api/v1/auth/token`

Request: `{ "username": "string", "password": "string" }`
Response `200`: `{ "access_token": "string", "expires_in": 3600 }`
Response `401`: `unauthenticated`
Response `429`: `rate_limited`, with a `Retry-After` header (seconds)

Rate-limited. Failed attempts are logged without logging the password or the submitted username.

After too many failed attempts within a sliding window, the endpoint returns `429 rate_limited` with a `Retry-After` header (seconds) and refuses every login attempt, even with the correct password, until the window allows another attempt. The lockout applies per client address and globally across all clients. The global limit is 4 times the per-client limit.

Defaults (configurable by the operator, so not guaranteed): 5 failed attempts per client within 900 seconds (`LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_SECONDS`). A successful login clears that client's failure count.

The account is a single owner account stored in the database. It is created and reset by a server command (`python -m app.cli.set_owner`); there is no signup endpoint. If no account exists, the endpoint returns `401`.

### Reminder object

```json
{
  "id": "uuid",
  "kind": "service | insurance_renewal | road_tax_renewal",
  "title": "string",
  "due_date": "YYYY-MM-DD|null",
  "due_odometer": 0,
  "notes": "string|null",
  "completed_on": "YYYY-MM-DD|null",
  "template_ref": "string|null",
  "status": "upcoming | overdue | completed",
  "overdue_by": ["date", "odometer"],
  "created_at": "timestamp",
  "updated_at": "timestamp"
}
```

`due_odometer` is an integer in kilometres, or `null`. `status` and `overdue_by` are computed by the server on read and are never stored or accepted in a request. `overdue_by` is empty unless `status` is `overdue`.

### Create and update

`POST` body: `id`, `kind`, `title`, `due_date`, `due_odometer`, `notes`, `template_ref`. `completed_on` is not accepted on create. Unknown fields are rejected (`extra=forbid`, as for service records).

`PATCH` body: any of `kind`, `title`, `due_date`, `due_odometer`, `notes`, `completed_on`. Omitted fields are unchanged. `due_date`, `due_odometer`, `notes` and `completed_on` may be set to `null`. `kind` and `title` may not be null. `template_ref` cannot be changed after create.

Validation (violations return `400 validation_error` with field details):

- `kind` is one of the three values.
- `title` is 1 to 200 characters after trimming.
- At least one of `due_date` and `due_odometer` is non-null, on create and after any `PATCH` is applied. The detail names both fields.
- `due_odometer` is a strict integer, `>= 0` and `<= 10,000,000` (the existing odometer bound).
- `due_odometer` must be null unless `kind` is `service` (proposal, Q4). Changing `kind` away from `service` with a due odometer still set is rejected.
- `due_date` is a valid date. Past dates are accepted (proposal, Q8). No upper bound other than a valid date from 2000-01-01 to 2200-12-31.
- `completed_on` is not in the future, judged against the current date in Asia/Kuala_Lumpur (UTC+8), the same rule as service-record dates after the owner decision of 2026-10-22 (this changes the earlier service-record rule, see "Changes to approved parts").
- `notes` is at most 5,000 characters. `template_ref` is at most 100 characters.
- No NUL characters in any string (existing rule).
- At most 500 reminders in total; a create beyond that returns `400 validation_error` on field `body` (proposed bound, keeps the list unpaginated).

Idempotent replay compares the content fields `kind`, `title`, `due_date`, `due_odometer`, `notes` and `template_ref`.

### List and status

`GET /api/v1/reminders` query:

- `today` (optional, `YYYY-MM-DD`): the date used to compute status. Defaults to the current date in Asia/Kuala_Lumpur (UTC+8, owner decision 2026-10-22), so the client does not need to send it. A malformed value returns `400 validation_error`.
- `include_completed` (optional boolean, default `false`).

Response `200`:

```json
{
  "items": [ { "...reminder": "..." } ],
  "current_odometer": {
    "km": 0,
    "source": "latest_service_record",
    "service_record_id": "uuid",
    "date": "YYYY-MM-DD"
  }
}
```

`current_odometer` is `null` when there is no service record (proposal, Q1). It is the `odometer` of the first service record in history order (latest `date`, then `created_at`, then `id`).

Status rules, used by both the server and the offline client:

- `completed_on` set: `completed`.
- Else `overdue` if `today > due_date` (`overdue_by` includes `date`), or if `current_odometer` is not null and `current_odometer.km > due_odometer` (includes `odometer`). Equality is not overdue.
- Else `upcoming`.

Order: overdue first, then upcoming, then completed. Within a group: `due_date` ascending with nulls last, then `due_odometer` ascending with nulls last, then `id`. There is no cursor, because the set is bounded.

### Offline writes and idempotency

Matches the existing service-record pattern (ADR-002). The client generates the reminder UUID, so a `POST` retry is safe: `201` first, then `200` on identical replay. Queue entry kinds are added for create, edit and delete of a reminder, with `record_id` set to the reminder id so create-then-edit coalesces, an edit after create is folded into the pending create, and a delete after an unsent create cancels both. A replayed `DELETE` returning `404` counts as success. `PATCH` is naturally repeatable. Completing is a `PATCH` of `completed_on`, and an offline reminder shows status computed on the device from the shared test vectors; the server value replaces it on the next sync. `400` and `409` mark the queue item failed and visible; `5xx`, `429` and network errors retry with backoff; `401` pauses the queue. Template accept offline queues one create per selected item.

### Changes to approved parts

One change to an approved part, by owner decision 2026-10-22: the service-record rule "date not in the future" is now judged against the current date in Asia/Kuala_Lumpur (UTC+8), not the UTC date. This removes the 00:00 to 08:00 rejection window. It needs the existing backend check (`services/api/app/schemas.py`), the web default date and hint, and their tests updated, and re-approval of this amendment. Timestamps (`created_at`, `updated_at`) stay UTC. No other endpoint, field or error code changes. Two further points for the owner:

1. The line "Not yet specified" below was edited only to remove "reminders" from its list.
2. If the owner picks the alternative in Q1 (an owner-entered current odometer), that would add a field to `Vehicle` or a new resource, which does change the approved vehicle contract and needs a separate amendment. The proposal avoids this.

### Create and update

### List and filters

`category` is one enum value; `from` and `to` are inclusive `YYYY-MM-DD` dates, either or both. Unknown category, malformed date, `from > to` and an invalid cursor return `400 validation_error`. Filters combine with AND and apply with `cursor`. Response: `{ "items": [ ... ], "next_cursor": "string|null" }`, the same cursor format as service records.

### Summary

`GET /api/v1/expenses/summary` returns `200`:

```json
{
  "currency": "MYR",
  "total_minor": 0,
  "count": 0,
  "by_category": [ { "category": "charging", "total_minor": 0, "count": 0 } ],
  "by_month": [ { "month": "YYYY-MM", "total_minor": 0, "count": 0 } ]

```

Computed on every request from the matching rows and never stored. Integer sums. `by_category` is ordered by `total_minor` descending then category; `by_month` by month descending. Categories or months with no rows are omitted. `month` is the first 7 characters of the expense `date` (no time zone conversion). Service record costs are not included (proposal, Q10). The same pure function runs on the device for offline totals (AC-41).

### Create and update (coverage)

`POST` body: `id`, `name`, `provider_type`, `start_date`, `end_date`, `km_limit`, `notes`, `source_kind` (default `owner_entered`), `verification_status` (default `unverified`; the web form sends `proposed` for template items), `source_note`, `template_ref`. `PATCH` body: any of `name`, `provider_type`, `start_date`, `end_date`, `km_limit`, `notes`, `verification_status`, `source_note`. `end_date`, `km_limit`, `notes`, `source_note` may be null. `source_kind` and `template_ref` cannot be changed after create.

Validation (`400 validation_error`):

- `name` 1 to 200 characters after trimming. `provider_type`, `source_kind`, `verification_status` are enum values.
- `start_date` required. `start_date` and `end_date` are `YYYY-MM-DD` strings between 2000-01-01 and 2200-12-31. Future start and past end are accepted.
- At least one of `end_date` and `km_limit` is non-null, on create and after any `PATCH`; the detail names both fields.
- `end_date >= start_date`.
- `km_limit` is a strict integer, `>= 1` and `<= 10,000,000`.
- `notes` at most 5,000 characters, `source_note` at most 200, `template_ref` at most 100. `template_ref` non-null requires `source_kind` `template`.
- At most 50 coverages (field `body`).

Idempotent replay compares all create content fields.

### Status rules (server and offline client, shared vectors)

`today` (optional query, `YYYY-MM-DD`) defaults to the current date in Asia/Kuala_Lumpur; malformed returns `400`. Current odometer is the same read as reminders (latest service record by `date`, `created_at`, `id`; `null` if none). Warranty claims never change it.

1. `expired` if `end_date` is set and `today > end_date` (`expired_by` has `date`), or the odometer is known and `> km_limit` (has `odometer`). Equality is not expired.
2. Else `not_started` if `today < start_date`.
3. Else `expiring_soon` if `end_date` is set and `end_date - today <= 90` days (has `date`), or the odometer is known and `km_limit - odometer <= 5,000` (has `odometer`). Thresholds are display-only (proposal, Q19).
4. Else `active`.

If the odometer is unknown the km conditions are not evaluated. The UI wording is "active by the dates and km you entered", never "covered" (AC-53).

List response `200`: `{ "items": [coverage], "current_odometer": { "km", "source": "latest_service_record", "service_record_id", "date" } | null }`. Order: `expiring_soon`, `active`, `not_started`, `expired`; within a status by `end_date` ascending (nulls last), then `name`, then `id`.

Validation (`400 validation_error`): `coverage_id` references an existing coverage (else a `400` on field `coverage_id`); `date` valid, from 2000-01-01, not after today in Asia/Kuala_Lumpur; `odometer` strict integer 0 to 10,000,000; `description` 1 to 500 characters; `status` is an enum value (proposal, Q21); `cost_covered_minor` null or a strict integer 0 to 10^12; `currency` MYR; `notes` at most 5,000; at most 500 claims. A claim date outside the coverage dates is accepted. `cost_covered_minor` is a record only: no expense is created and no total changes.

### Offline writes and idempotency

Same pattern as reminders. Queue kinds are added for coverage and claim create, edit and delete, with `record_id` set to the entity id. Ordering: a coverage create is sent before the claim creates that reference it; if it fails, its dependent claim creates are shown as blocked and not sent. Deleting an unsent coverage cancels its unsent claims. Deleting a sent coverage while claim creates are pending: the pending claim creates are dropped locally with a visible notice. A replayed `DELETE` returning `404` counts as success. `400` and `409` mark the item failed and visible.

### Errors

As for Expenses. A claim `POST` or `PATCH` with an unknown `coverage_id` is `400 validation_error` on `coverage_id`; `GET`, `PATCH`, `DELETE` of an unknown id is `404 not_found`.

### Proposal object

```json
{
  "id": "uuid",
  "condition": "date_vs_km_warranty | date_vs_km_service | charging_cost_drift",
  "status": "proposed | accepted | dismissed",
  "inputs": { "km_to_limit": 0, "days_to_expiry": 0, "projected_limit_date": "YYYY-MM-DD" },
  "source_refs": [ { "kind": "warranty_coverage | reminder | expense", "id": "uuid" } ],
  "explanation": "string|null",
  "explanation_status": "model | unavailable | disabled | limit_reached | invalid_output",
  "urgency": "low | normal | high | null",
  "suggestion": { "kind": "review_reminder", "title": "string", "due_date": "YYYY-MM-DD|null", "due_odometer": 0 },
  "provenance": { "rule_version": 1, "prompt_version": 1, "model_id": "string|null" },
  "created_at": "timestamp",
  "updated_at": "timestamp",
  "decided_at": "timestamp|null"
}
```

- `inputs` has the fields for its condition only: `km_to_limit`, `days_to_expiry`, `projected_limit_date` for the two date-versus-km conditions; `latest_cost_per_kwh_sen`, `average_cost_per_kwh_sen`, `latest_date` for charging drift. These are exactly the values sent to the model.
- `suggestion` is `null` for `charging_cost_drift` (it only informs). For the date-versus-km conditions it is built by code from fixed text. Its title never contains owner free text.
- `explanation` is model text, shown as the model's opinion, never as fact. `prompt_version` and `model_id` are `null` when no model was used.
- Nothing is computed on read. A proposal is a stored record of what was observed when it was raised.

### Run response (`POST /advisory/checks`)

```json
{
  "created": [ { "...proposal": "..." } ],
  "unchanged": 0,
  "skipped": [ { "condition": "string", "reason": "not_enough_data" } ],
  "model": { "status": "used | disabled | unavailable | limit_reached", "calls_this_month": 0, "monthly_limit": 60 }
}
```

`skipped` explains why a check found nothing to evaluate (for example fewer than 2 service records in the window), so silence is never ambiguous. One model call is made per new finding at most, and none when `model.status` is not `used`.

### Decide (`PATCH`)

Only a `proposed` item can be decided. Repeating the same decision returns `200` with the item. A different decision on an already decided item returns `409 conflict`. Unknown id: `404 not_found`. A body with any other field or value: `400 validation_error`. Deciding changes only the proposal; accepting does not create a reminder (the client does that with an ordinary `POST /reminders`).

### Status and audit

`GET /advisory/status` returns `200 { "model_enabled": false, "model_id": "string|null", "calls_this_month": 0, "monthly_limit": 60, "month": "YYYY-MM" }`. It never returns the key or whether one is set beyond `model_enabled`.

`GET /advisory/model-calls` returns `{ "items": [ { "id", "proposal_id", "called_at", "model_id", "request_text", "response_text", "input_tokens", "output_tokens", "outcome" } ] }`. This is the owner's audit of what left the host.

### Errors

As for Reminders. Additionally, the model being off, unreachable or over its limit is **not** an error: the run succeeds and reports it under `model.status`.

### Offline

Online only in the first build. Proposals and decisions are not cached or queued offline. The rest of the app is unaffected when this screen is unavailable.
