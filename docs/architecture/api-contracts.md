## Conventions

- Base path: `/api/v1`
- JSON only. Field names are `snake_case`.
- IDs are UUIDs, generated by the client for creates so retries are idempotent.
- Money is an integer in minor units (sen; 1 MYR = 100 sen) with a `currency` field.
- `currency` is an ISO 4217 three-letter code and defaults to `MYR` when omitted. Only `MYR` is accepted for now; any other value returns `400 validation_error` (multi-currency is out of scope).
- Distances are integers in kilometres. This includes `odometer`.
- Timestamps are ISO 8601 UTC. Dates are `YYYY-MM-DD`.
- All endpoints except `/health` need `Authorization: Bearer <token>`.
- Every response under `/api` (including errors) carries `Cache-Control: no-store`.
- Request bodies larger than 64 KiB (65,536 bytes) are rejected with `400 validation_error` and a detail `{ "field": "body", "issue": "request body is too large" }`.
- Upper bounds (violations return `400 validation_error`): `odometer` <= 10,000,000 km; every `*_minor` money field (`cost_minor`, `purchase_price_minor`) <= 10^12 sen.

## Error shape

```json
{
  "error": {
    "code": "validation_error",
    "message": "Human-readable summary",
    "details": [{ "field": "cost_minor", "issue": "must be >= 0" }]
  }
}
```

| Status | Code | Meaning |
|---|---|---|
| 400 | `validation_error` | Body failed validation |
| 401 | `unauthenticated` | Missing or invalid token |
| 404 | `not_found` | Resource does not exist |
| 405 | `method_not_allowed` | HTTP method not supported on this path |
| 409 | `conflict` | Same ID with different content |
| 429 | `rate_limited` | Too many failed login attempts. Response has a `Retry-After` header in seconds. The login attempt is refused even if the password is correct (hard lockout, owner decision) |
| 500 | `internal_error` | Unexpected server error. Uses the same error shape; `details` is empty and no internal information is exposed |

## Endpoints

### Health

`GET /health` returns `200 {"status": "ok"}`. No authentication.

### Authentication

`POST /api/v1/auth/token`

Request: `{ "username": "string", "password": "string" }`
Response `200`: `{ "access_token": "string", "expires_in": 3600 }`
Response `401`: `unauthenticated`
Response `429`: `rate_limited`, with a `Retry-After` header (seconds)

Rate-limited. Failed attempts are logged without logging the password or the submitted username.

After too many failed attempts within a sliding window, the endpoint returns `429 rate_limited` with a `Retry-After` header (seconds) and refuses every login attempt, even with the correct password, until the window allows another attempt. The lockout applies per client address and globally across all clients. The global limit is 4 times the per-client limit.

Defaults (configurable by the operator, so not guaranteed): 5 failed attempts per client within 900 seconds (`LOGIN_MAX_FAILURES`, `LOGIN_WINDOW_SECONDS`). A successful login clears that client's failure count.

The account is a single owner account stored in the database. It is created and reset by a server command (`python -m app.cli.set_owner`); there is no signup endpoint. If no account exists, the endpoint returns `401`.

### Reminder object

```json
{
  "id": "uuid",
  "kind": "service | insurance_renewal | road_tax_renewal",
  "title": "string",
  "due_date": "YYYY-MM-DD|null",
  "due_odometer": 0,
  "notes": "string|null",
  "completed_on": "YYYY-MM-DD|null",
  "template_ref": "string|null",
  "status": "upcoming | overdue | completed",
  "overdue_by": ["date", "odometer"],
  "created_at": "timestamp",
  "updated_at": "timestamp"
}
```

`due_odometer` is an integer in kilometres, or `null`. `status` and `overdue_by` are computed by the server on read and are never stored or accepted in a request. `overdue_by` is empty unless `status` is `overdue`.

### Create and update

`POST` body: `id`, `kind`, `title`, `due_date`, `due_odometer`, `notes`, `template_ref`. `completed_on` is not accepted on create. Unknown fields are rejected (`extra=forbid`, as for service records).

`PATCH` body: any of `kind`, `title`, `due_date`, `due_odometer`, `notes`, `completed_on`. Omitted fields are unchanged. `due_date`, `due_odometer`, `notes` and `completed_on` may be set to `null`. `kind` and `title` may not be null. `template_ref` cannot be changed after create.

Validation (violations return `400 validation_error` with field details):

- `kind` is one of the three values.
- `title` is 1 to 200 characters after trimming.
- At least one of `due_date` and `due_odometer` is non-null, on create and after any `PATCH` is applied. The detail names both fields.
- `due_odometer` is a strict integer, `>= 0` and `<= 10,000,000` (the existing odometer bound).
- `due_odometer` must be null unless `kind` is `service` (proposal, Q4). Changing `kind` away from `service` with a due odometer still set is rejected.
- `due_date` is a valid date. Past dates are accepted (proposal, Q8). No upper bound other than a valid date from 2000-01-01 to 2200-12-31.
- `completed_on` is not in the future, judged against the current date in Asia/Kuala_Lumpur (UTC+8), the same rule as service-record dates after the owner decision of 2026-10-22 (this changes the earlier service-record rule, see "Changes to approved parts").
- `notes` is at most 5,000 characters. `template_ref` is at most 100 characters.
- No NUL characters in any string (existing rule).
- At most 500 reminders in total; a create beyond that returns `400 validation_error` on field `body` (proposed bound, keeps the list unpaginated).

Idempotent replay compares the content fields `kind`, `title`, `due_date`, `due_odometer`, `notes` and `template_ref`.

### List and status

`GET /api/v1/reminders` query:

- `today` (optional, `YYYY-MM-DD`): the date used to compute status. Defaults to the current date in Asia/Kuala_Lumpur (UTC+8, owner decision 2026-10-22), so the client does not need to send it. A malformed value returns `400 validation_error`.
- `include_completed` (optional boolean, default `false`).

Response `200`:

```json
{
  "items": [ { "...reminder": "..." } ],
  "current_odometer": {
    "km": 0,
    "source": "latest_service_record",
    "service_record_id": "uuid",
    "date": "YYYY-MM-DD"
  }
}
```

`current_odometer` is `null` when there is no service record (proposal, Q1). It is the `odometer` of the first service record in history order (latest `date`, then `created_at`, then `id`).

Status rules, used by both the server and the offline client:

- `completed_on` set: `completed`.
- Else `overdue` if `today > due_date` (`overdue_by` includes `date`), or if `current_odometer` is not null and `current_odometer.km > due_odometer` (includes `odometer`). Equality is not overdue.
- Else `upcoming`.

Order: overdue first, then upcoming, then completed. Within a group: `due_date` ascending with nulls last, then `due_odometer` ascending with nulls last, then `id`. There is no cursor, because the set is bounded.

### Offline writes and idempotency

Matches the existing service-record pattern (ADR-002). The client generates the reminder UUID, so a `POST` retry is safe: `201` first, then `200` on identical replay. Queue entry kinds are added for create, edit and delete of a reminder, with `record_id` set to the reminder id so create-then-edit coalesces, an edit after create is folded into the pending create, and a delete after an unsent create cancels both. A replayed `DELETE` returning `404` counts as success. `PATCH` is naturally repeatable. Completing is a `PATCH` of `completed_on`, and an offline reminder shows status computed on the device from the shared test vectors; the server value replaces it on the next sync. `400` and `409` mark the queue item failed and visible; `5xx`, `429` and network errors retry with backoff; `401` pauses the queue. Template accept offline queues one create per selected item.

One change to an approved part, by owner decision 2026-10-22: the service-record rule "date not in the future" is now judged against the current date in Asia/Kuala_Lumpur (UTC+8), not the UTC date. This removes the 00:00 to 08:00 rejection window. It needs the existing backend check (`services/api/app/schemas.py`), the web default date and hint, and their tests updated, and re-approval of this amendment. Timestamps (`created_at`, `updated_at`) stay UTC. No other endpoint, field or error code changes. Two further points for the owner:

1. The line "Not yet specified" below was edited only to remove "reminders" from its list.
2. If the owner picks the alternative in Q1 (an owner-entered current odometer), that would add a field to `Vehicle` or a new resource, which does change the approved vehicle contract and needs a separate amendment. The proposal avoids this.

### Summary

`GET /api/v1/expenses/summary` returns `200`:

```json
{
  "currency": "MYR",
  "total_minor": 0,
  "count": 0,
  "by_category": [ { "category": "charging", "total_minor": 0, "count": 0 } ],
```

### Create and update (coverage)

`POST` body: `id`, `name`, `provider_type`, `start_date`, `end_date`, `km_limit`, `notes`, `source_kind` (default `owner_entered`), `verification_status` (default `unverified`; the web form sends `proposed` for template items), `source_note`, `template_ref`. `PATCH` body: any of `name`, `provider_type`, `start_date`, `end_date`, `km_limit`, `notes`, `verification_status`, `source_note`. `end_date`, `km_limit`, `notes`, `source_note` may be null. `source_kind` and `template_ref` cannot be changed after create.

Validation (`400 validation_error`):

- `name` 1 to 200 characters after trimming. `provider_type`, `source_kind`, `verification_status` are enum values.
- `start_date` required. `start_date` and `end_date` are `YYYY-MM-DD` strings between 2000-01-01 and 2200-12-31. Future start and past end are accepted.
- At least one of `end_date` and `km_limit` is non-null, on create and after any `PATCH`; the detail names both fields.
- `end_date >= start_date`.
- `km_limit` is a strict integer, `>= 1` and `<= 10,000,000`.
- `notes` at most 5,000 characters, `source_note` at most 200, `template_ref` at most 100. `template_ref` non-null requires `source_kind` `template`.
- At most 50 coverages (field `body`).

Idempotent replay compares all create content fields.

### Status rules (server and offline client, shared vectors)

`today` (optional query, `YYYY-MM-DD`) defaults to the current date in Asia/Kuala_Lumpur; malformed returns `400`. Current odometer is the same read as reminders (latest service record by `date`, `created_at`, `id`; `null` if none). Warranty claims never change it.

1. `expired` if `end_date` is set and `today > end_date` (`expired_by` has `date`), or the odometer is known and `> km_limit` (has `odometer`). Equality is not expired.
2. Else `not_started` if `today < start_date`.
3. Else `expiring_soon` if `end_date` is set and `end_date - today <= 90` days (has `date`), or the odometer is known and `km_limit - odometer <= 5,000` (has `odometer`). Thresholds are display-only (proposal, Q19).
4. Else `active`.

If the odometer is unknown the km conditions are not evaluated. The UI wording is "active by the dates and km you entered", never "covered" (AC-53).

List response `200`: `{ "items": [coverage], "current_odometer": { "km", "source": "latest_service_record", "service_record_id", "date" } | null }`. Order: `expiring_soon`, `active`, `not_started`, `expired`; within a status by `end_date` ascending (nulls last), then `name`, then `id`.

### Offline writes and idempotency

Same pattern as reminders. Queue kinds are added for coverage and claim create, edit and delete, with `record_id` set to the entity id. ```

- The numbers are shape only, not a reading. Every value under `readings` may be `null` (missing, empty or out of range), shown as "no reading", never as zero. With `status` `off`, `readings` is all `null`, `observed_at` and `received_at` are `null`, and no Zeekr call is made.

- `observed_at` is the car's own update time (UTC). `received_at` is when the server got it. The screen shows both in Asia/Kuala_Lumpur.
- Distances are integers in km, tyre pressure integer kPa (owner-confirmed unit), `battery_percent` a number from 0 to 100 (the car's precision is unverified; the model stores one decimal).
- **Never present** in the response, the logs or the table: position, lock state, door state, VIN, plate, nickname, and the raw Zeekr reply. A test checks the serialised response.
- Failures show fixed text. Nothing from the Zeekr library or server appears in the response or logs.

### Spacing and who triggers a read

- The web page calls the card endpoint on a timer every `interval_minutes`, and on pull-down, **only while the Vehicle page is open and visible**. The server never polls Zeekr in the background (owner decision A).
- The server makes at most one real Zeekr read per `interval_minutes`, however many calls arrive. Calls inside the window return the stored reading with `served_from: "cache"` and store nothing.
- Concurrent calls are serialised, so two pages cannot cause two reads.

## Complete service and daily odometer (APPROVED by the owner, 2026-11-03; ADR-009 amendment)

Owner request and answers, 2026-11-03: tick a service reminder on the reminder page, enter the actual date, service centre and odometer, and have that update the Service page; the next reminder is the actual odometer plus the interval; from 30 days before a service is due until it is done, the odometer is refreshed daily from the car. Cost may be zero. Warranty does not use the live odometer. The unattended daily Zeekr login is accepted (ADR-009 amendment).

No new table and no migration. Nothing here is built.

### Endpoint

| Method | Path | Notes |
|---|---|---|
| `POST` | `/api/v1/reminders/{id}/complete-service` | One all-or-nothing transaction. Online only |

Body (`extra=forbid`): `record_id` (uuid, client-generated), `next_id` (uuid, client-generated), `date`, `odometer`, `provider` (service centre, optional), `description` (optional, default is the reminder title), `cost_minor` (integer sen, `>= 0`, zero allowed, default 0), `notes` (optional). `date`, `odometer`, `provider`, `cost_minor`, `notes` and the `description` bound follow the service-record rules (`date` not in the future in Asia/Kuala_Lumpur).

In one transaction the server:

1. Creates a service record with `record_id` and the entered values (so the Service page and the current odometer update).
2. Sets the reminder's `completed_on` to `date`.
3. Creates the next reminder `next_id`, only if the completed reminder has a `template_ref` of the form `awd-performance-service:<version>:<n>`. The interval comes from the current template (40,000 km, 24 months, whichever comes first):
   - `due_odometer` = entered `odometer` + 40,000 (the actual reading, not the nominal checkpoint). A result above 10,000,000 returns `400`.
   - `due_date` = entered `date` + 24 months, clamped to the month's last day. The date is always service date + 24 months. The odometer never moves it and it never moves the odometer limit, so when the two disagree the 24-month date stands (owner answer 1). The existing status rule still marks the reminder overdue by whichever limit is passed first.
   - `title` = `Next service (<due_odometer> km)`; `kind` = `service`; `template_ref` = the same value; `notes` = null.
   - A reminder with no `template_ref` completes and records the service but creates no next reminder. The response says so (`next_reminder: null`).

Response `201`: `{ "service_record": {record}, "reminder": {completed reminder}, "next_reminder": {reminder} | null }`.

Replay: the same `record_id`, `next_id` and body returns `200` with the same result and writes nothing. The same ids with different content return `409 conflict`.

| Case | Status and code |
|---|---|
| Body fails validation, bad UUID, odometer above bound | `400 validation_error` |
| Reminder not `kind` service, or already completed | `400 validation_error` on field `body` |
| `odometer` lower than the current odometer for reminders (newest service record or stored live reading) | `400 validation_error` on field `odometer` (owner decision, 2026-11-03; no override) |
| 500 reminders already exist | `400 validation_error` on field `body`; nothing is written |
| Unknown reminder id | `404 not_found` |
| Ids reused with different content | `409 conflict` |

Review change (owner decision, 2026-11-03): an odometer lower than the current odometer for reminders is rejected, to stop a typo from becoming the newest record. A lower figure that is really right means fixing the older record first. A replay is judged before this check, so a replay of an accepted call still returns `200`.

Data model change (owner decision, 2026-11-03, migration `0010`): `service_record` gains a nullable `reminder_id` (foreign key to `reminder`, `ON DELETE SET NULL`). Complete service sets it. A replay must match the same reminder, so the same ids sent to another reminder return `409`. Records made any other way keep `reminder_id` null and are never a replay. The field is not in any response.

Offline: the button is disabled with a message. The three writes are not queued, so a replay cannot create a second next reminder. The existing "Mark complete" and "Edit" keep their offline behaviour for the other reminder kinds.

Web: for a service reminder that is not completed, the detail page shows "Complete service" (replacing "Mark complete") and a form with Actual service date, Service centre, Odometer (km), Cost (MYR, zero allowed), Description and Notes. The odometer is prefilled from the current odometer and can be changed. Insurance and road-tax reminders keep "Mark complete".

### Current odometer for reminders

`current_odometer` on the reminders list gains `source: "live_reading"`. The server takes the larger kilometre figure of the newest stored live reading and the latest service record (an odometer does not go down, so a smaller figure is a stale or wrong one). With live readings off or none stored, behaviour is unchanged. Warranty and wear status keep using the service record only (owner answer 4). The live reading stays out of the model prompt.

### Daily read (ADR-009 amendment)

A background task starts with the API only if `ZEEKR_LIVE_ENABLED` is true. It reads the car at most once per Kuala Lumpur day, at or after 08:00 KL, only while at least one open service reminder has `due_date` and today is on or after `due_date` minus 30 days. It keeps running after the due date and stops when no such reminder is open, that is when the service is completed. It uses the existing lock, spacing, back-off and stop-after-failures, and stores through the existing `live_reading` path. A reading stored by a Vehicle page visit that day counts as the day's read. If the provider has stopped, the task does nothing and logs one line without any value. No setting is added. The 08:00 time is a constant in code.

### Acceptance criteria (draft)

- A complete-service call creates one service record, completes the reminder and creates one next reminder with `due_odometer` = actual + 40,000 and `due_date` = actual date + 24 months, all or nothing. A failure at any step leaves nothing written.
- Replaying it changes nothing. Different content under the same ids returns `409`.
- A reminder without a `template_ref` creates no next reminder.
- Cost zero is accepted; a negative cost, a future date or a non-service reminder is rejected.
- The Service page lists the new record, and the current odometer reflects it.
- With the flag off, no background task runs and no Zeekr call is made.
- The daily task does not read outside the 30-day window, after the service is completed, more than once per KL day, or when the provider has stopped.
- Warranty and wear figures do not change when a live reading is stored.

### Amendment: Sentry command (ADR-010; owner approved 2026-11-03; migration `0012`)

The one command the app may send to the car. Nothing else is added: no other command, no schedule, no automatic send.

| Method | Path | Meaning |
|---|---|---|
| `POST` | `/api/v1/vehicle/sentry` | Body `{"desired": "on" \| "off"}`. Sends one Sentry command, waits `SENTRY_CONFIRM_WAIT_SECONDS` (default 15), reads the state back. `200`, `400`, `401`, `404`, `409`, `502` |
| `GET` | `/api/v1/vehicle/sentry/log?limit=` | The last commands, newest first. `limit` 1 to 100, default 20. `200`, `400`, `401` |

- Token required, `no-store`, `400 validation_error` (never 422) for any body but exactly `on` or `off`.
- `200` body: `desired`, `sent` (false only when the car already reported the wanted state, so nothing was sent), `state_after` (`on`, `off` or `null`) and `confirmed` (`state_after == desired`). `confirmed: false` means the car had not reported the change at the read-back; it is not a failure and the command is not repeated.
- `404 not_found`: live readings are off (`ZEEKR_LIVE_ENABLED` false). Nothing is sent.
- `409 conflict`: another send is in progress, a status read holds the Zeekr lock for more than 5 seconds, or the last logged command was less than 60 seconds ago.
- `502 upstream_error` (new code, used by this endpoint only): the car's service refused the command, or the login or first read failed. The message is fixed text, never Zeekr's. A refusal is not retried.
- It uses the provider's one logged-in session, its daily login cap and the same lock, so a send and a status read never overlap. It does not change the provider's failure count or back-off.
- Table `car_command_log`: `id`, `created_at` (UTC), `desired` (`on` or `off`), `source` (`manual`), `result` (`sent`, `refused` or `failed`), `state_after` (`on`, `off` or null). CHECK constraints refuse any other value. No payload, reply body, VIN or position. Kept 12 months. A send that finds the car already in the wanted state sends and logs nothing.
- **Setting (owner approved 2026-11-04):** `SENTRY_CONFIRM_WAIT_SECONDS`, integer, default 15, 5 to 30; outside that range the API refuses to start. The name is the agent's proposal, approved by the owner. No endpoint, field or table changed.
- The web switch is separate from the read-only indicators. It shows the state the car last reported, always asks first when flipped, and after the send moves to the `state_after` the API returns (never to the state that was asked for). `confirmed: false` is shown as "did not take effect". It shows only fixed wording, taken from `confirmed` and the status code.
- Acceptance criteria: (13) the body is exactly `on` or `off`, anything else is 400 and sends nothing; (14) one send is one library call with the constant payload; (15) the state shown after is what the car reports, and an unreadable state after is `null`; (16) a refusal is 502 with fixed text and no retry; (17) a second send within 60 seconds, or while one is in progress, is 409 and sends nothing; (18) the log holds no payload or reply; (19) only the Sentry command module names the write method.

### Amendment: Sentry state pushed to open pages (ADR-010; owner approved 2026-11-05)

So a second open page (for example a phone) shows the switch change made on another page. Option A with a re-sync, approved by the owner. No "who changed it" label.

| Method | Path | Meaning |
|---|---|---|
| `GET` | `/api/v1/vehicle/sentry/state` | The last Sentry state this API saw after a send, from memory. `200` body `{"state": "on" \| "off" \| null, "at": <UTC time> \| null}`. `null` after an API restart or before any send. `200`, `401` |
