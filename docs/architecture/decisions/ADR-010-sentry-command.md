# ADR-010: One command to the car, Sentry on and off

Status: **accepted by the owner on 2026-11-03 (approvals recorded in `docs/product/sentry-control-and-geofence-proposal.md`). The payload is verified for both directions on the owner's car (see the build records).**

## Context

ADR-008 and ADR-009 say the app sends no commands to the car, and tests ban the Zeekr library's write methods in the read adapter and the dump tool. The owner now wants to switch Sentry on and off by hand from the app, after the read-only Sentry indicator was confirmed against the car.

## Decision

- The app may send **one** kind of command: Sentry on or off. Nothing else. No lock, door, window, climate, charge or any other command, and no unattended or automatic command (narrowed by ADR-011 to one exception, automatic Sentry on behind a toggle and a host switch; ADR-011 is accepted, its build is not approved yet). The geofence alert (proposal, Piece B) is advisory only and never sends this command.
- The call lives in one module, `app/adapters/zeekr_sentry_command.py`. The service id, key and value are constants there; no caller can pass another command, service, key or value. The read-only adapter and the dump tool keep their ban on write methods, and a test fails if any other file under `app/` names the write method.
- The payload comes from a third-party Home Assistant integration for the same car model (MIT licence, not tested by the owner): service `RSM`, one setting with key `rsm` and value `6`; command `start` to switch on and `stop` to switch off. This is **unverified** until the owner's first run.
- **First send is owner-run.** A CLI (`python -m app.cli.zeekr_sentry_send`) makes one login, reads `vstdModeState`, sends one command, waits, reads it again and prints only the two values and whether Zeekr accepted the call. The agent never runs it. Only after the owner reports a watched, correct read-back does the app get an endpoint and a button.
- After any send the state shown is what the car reports on a later read, never an assumption that the command worked.
- The account used is the second account, as for the reads. Whether it may send commands is unknown.

## Consequences

- The "no commands to the car" rule is narrowed, not removed. ADR-008 "Act" stays advisory.
- A wrong payload could do something unintended on the car or get the account flagged. Mitigation: the owner-run first send, one command, watched.
- Zeekr's terms are unverified, and a command is a stronger action than a read.
- The app does not know how long Sentry has been on.
- Later steps (endpoint, button, `car_command_log` table, migration `0012`) are separate, need a fresh encrypted export before the deploy, and are recorded here as build records.

## Not allowed

- Any other command, including the library's charge and travel plan writers.
- Sending from a schedule, a rule or the model.
- Logging or storing the payload, the reply body, the VIN or any position.

## Build records

- **First send, owner-run (2026-11-04).** The owner ran `app.cli.zeekr_sentry_send --on`: state before off, Zeekr accepted the call, state after 15 seconds on, and the owner saw Sentry come on in the car (owner-observed). The owner then ran `--off`: state before on, accepted, state after off, and the owner observed Sentry off. So `RSM` / `rsm` = `6` with `start` and `stop` is **confirmed** on this car, with the second account, for one on/off cycle. Not covered: other cars or software versions, or whether Zeekr changes it later. The "unverified" label on the payload is dropped.
- **Endpoint, log and button (2026-11-04; not deployed).** `POST /api/v1/vehicle/sentry`, `GET /api/v1/vehicle/sentry/log`, table `car_command_log` (migration `0012`) and a confirm-first button on the live card, as in `api-contracts.md` (Amendment: Sentry command). Decisions inside the approved scope: the 60-second spacing is counted from the last logged command; the send shares the provider's lock, session and login cap; a status read that holds the lock for over 5 seconds makes the send a 409; the web request waits up to 45 seconds because the server waits about 15 for the car. The new error code `upstream_error` (502) is used by this endpoint only. Tests use a fake vehicle; the autouse guard still blocks the real client, and a test fails if any file but `zeekr_sentry_command.py` names the write method.
- **Not verified:** the button on a phone, behaviour with two pages open, how Zeekr treats repeated sends, and whether a send is slower than 45 seconds on a bad day.
- **Owner trial and web fix (2026-11-04; web only, not deployed).** The owner pressed Send on the host. The card still showed the older reading ("No newer reading yet", 5-minute minimum spacing), so the Sentry state and the button did not follow the car. Fix, option A chosen by the owner: after a send, the page keeps the state the car reported at read-back, shows it as "Sentry: on/off, read from the car at <time>" and offers the next button from it, until a newer card reading arrives. No API change, no migration, no extra read of the car. A `null` state after sets nothing. Not chosen: merging the read-back into the stored card reading (option B), which would store a partial reading and change the provider and contract.
- **First send from the app, owner trial (2026-11-04; owner-reported, the page text was pasted).** On the host, with the deployed `a999fdf` build, the owner pressed Send (Sentry off) from the Vehicle page. After the web fix (`a638bf5`) the page showed the card's own reading (07:37 KL, Sentry On) and, below it, the line "Sentry: off, read from the car at 07:41 (KL)", with the button offering "Turn Sentry on". The owner reported that the result line said "Sentry: off" (the exact wording was not pasted) and that the Sentry off was seen on the car. So one send from the app, in the off direction, worked end to end on the owner's car. **Not covered:** the on direction from the app, the command log (not seen), the button on a phone, two pages open at once, how Zeekr treats repeated sends.
- **Separate Sentry switch and configurable wait (2026-11-04; owner request and approval; not deployed).** Sentry is taken out of the read-only "Reported on / off" list and shown as its own switch, labelled as the one control. It shows the state the car last reported; flipping it asks to confirm, sends once, and after the wait the switch moves to the `state_after` the API returns. If the car did not change, the page says the command "did not take effect" and the switch stays at the state the API returned. The wait is the host setting `SENTRY_CONFIRM_WAIT_SECONDS` (default 15, 5 to 30, otherwise the API refuses to start); the web request now waits up to 60 seconds. No endpoint, field or migration changed. The one-at-a-time rule, the 60-second spacing and fixed wording are unchanged. The owner-run CLI keeps its own fixed 15 seconds.
- **First send from the separate switch, owner trial (2026-11-05; owner-reported, the page text was pasted).** On the host, with the deployed `53c9716` build, the owner confirmed the on-screen prompt "Send Sentry off" from the Vehicle page. The page then showed "The car reports Sentry off.", the switch moved from On to Off, and the line "Sentry: off, read from the car at 07:37 (KL)" replaced the earlier "on, 07:35" line, while the card's own reading was still the older 00:10 one (received 07:33). The owner reported "Sentry worked properly" (read as: the car's Sentry went off; the owner did not separately describe what was seen on the car). So the switch follows the API's read-back without a card refresh, as requested, and the "Reported on / off" list no longer holds Sentry. **Not covered:** the "did not take effect", 409 and 502 paths on the real car; the on direction from the switch; a wait other than the default (the owner reported `SENTRY_CONFIRM_WAIT_SECONDS` was left at the default 15, so the configured value has not been exercised on the host); the command log (not seen); the switch on a phone; two pages open at once. Observation, not a finding: the card's reading was about 7 hours old when received (00:10 stamped, 07:33 received); the cause is unknown.
- **Sentry state pushed to open pages (2026-11-05; owner approved option A with a re-sync, the contract addition, and no "who changed it" label; built, not deployed).** Why: with a desktop and a phone open, a send from one left the other showing the old switch, because only the sender got the result. Added `GET /api/v1/vehicle/sentry/state` (last state this API saw after a send) and `GET /api/v1/vehicle/sentry/events` (Server-Sent Events). The state is held in memory only (`SentryStateHub`): no table, no migration, a restart forgets it, and it never triggers a read of the car or carries any other data. A send that ends with a readable `state_after` publishes it, including a send that found the car already in the wanted state. Keepalive comment every 20 s, which also re-checks the token so an expired login ends the stream. At most 4 streams, the fifth gets `429 rate_limited`. The page reads the stream with `fetch` (the Bearer header), opens it only while visible and signed in, re-syncs from the state `GET` on load, on becoming visible and on connect, and reconnects with a 2 to 30 s back-off. A pushed state counts only while newer than the card's reading, as for a send from the same page. Proxy: a throwaway Caddy 2.11 container with a plain `reverse_proxy` delivered four events 1.5 s apart as sent, so no `flush_interval` was added (tested with a stand-in upstream, not the real API). **Not verified:** the real two-device case, the phone suspending and resuming a stream, and a long-lived stream through the host's `web` container.
- **Two-device trial of the state push (2026-11-05; owner-reported, short replies, no page text or log pasted).** On the host with the deployed `7c7cf2e` build, the owner ran the two-device test (desktop plus phone) and reported "All tests passed". Follow-up replies, recorded as given: the phone took "almost immediate" to follow a send from the desktop; "1-2 minutes" (read as how long the phone was locked, not confirmed); after unlock the phone "showed the correct state after the command was issued from the desktop"; "Yes" (to which question is not clear, possibly that the phone was on the LAN over plain HTTP); and "Yes On was sent", so the on direction was sent from the new switch. **Still not recorded:** what the API log showed for the `state` and `events` requests, and a lock longer than about two minutes. Treat the real-device behaviour as owner-reported, not independently checked. The iPhone checks (offline shell, install, pull-down) are still deferred, because they need HTTPS.

- **Control moved to the Sentry tab (owner request, 2026-11-06; web only, not deployed).** The Sentry switch, its confirm step, the result line and the "read from the car" line now live on the Sentry tab (`/sentry`), under the geofence notice. The Vehicle page shows readings only and says so. Earlier entries above that mention the Vehicle page are history. The command, its limits and the API are unchanged: manual only, one send per confirm, no automatic send. The Sentry tab asks for the live card once on open, when it becomes visible and on Refresh, with no timer. The tests that exercised the control on `/vehicle` now use `/sentry`, and one test checks the Vehicle page has no Sentry control. The iPhone check is deferred, not run.

- **Result line clears on Refresh (2026-11-06, web only, not deployed).** The owner's paste showed the card at Sentry Off (07:34 KL) under the old result line "The car reports Sentry on." from a send at 07:18, because the line stayed until the next send. Pressing Refresh now clears it. The line still stays after a send, until Refresh or the next send. A reading that arrives on opening or on the page becoming visible does not clear it (this keeps the line when the app goes offline mid-send). The owner later said they sent Sentry commands from the iPhone during that time (owner-reported in words; the commands, their order and the command log were not seen), which explains the change from on to off. The iPhone view was a separate page from the one that held the older result line.
